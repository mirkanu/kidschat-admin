## Integration Findings

### Monthly-cap dead-field chain (blocker)

```
┌──────────────────────────┐
│ balance_state            │
│  monthlySpendEur: 0      │  ← initialized, never incremented
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ evaluateChildState       │
│  monthlyCapExhausted =   │
│   0 >= 2.00 → false      │  ← always false
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────┐
│ UsageBars                │
│  monthlyPercent = 0%     │  ← stuck
└──────────────────────────┘
```

Root cause: Phase 15-04 designed the schema with a cumulative month-to-date field but shipped only the read/reset path. No write path. `grep -rn '\$inc.*monthlySpendEur' src tests` returns zero matches.

Additional concern: `topUpDailyBudget` uses `$set: { tokenCredits: credits }` — it **overwrites** rather than increments, so even if we accumulate monthly spend from token delta before reset, parent top-ups added before midnight UTC would be lost on the daily reset.

**Fix options** (not in audit scope — follow-up):
- **A. Daily-reset delta computation.** Before topping up, compute `yesterdaySpend = dailyCap - currentRemaining`, `$inc` into `monthlySpendEur`. Drawback: today's spend not visible until tomorrow.
- **B. Option A + live UI computation.** `displayedMonthlySpend = monthlySpendEur + (dailyCap - remainingEur)` in `evaluateChildState` — shows month-to-date including today.
- **C. Fix the `$set` → `$inc` clobber for top-ups.** Separate the "set baseline" path (cron) from the "add" path (parent top-up). Or keep a `bonusTokenCredits` column that survives midnight.
