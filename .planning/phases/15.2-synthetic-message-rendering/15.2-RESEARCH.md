# Phase 15.2: Synthetic Message Rendering — Research Findings

**Researched:** 2026-04-11
**Domain:** LibreChat message rendering pipeline, React Query cache, MongoDB message schema
**Confidence:** HIGH — root cause confirmed empirically with live DB queries and LibreChat source code reading

---

## Root Cause

**Two-part failure. The primary blocker is React Query cache staleness. A secondary issue is messageId format.**

### Primary: React Query cache is NEVER re-fetched during an active session

LibreChat's message query (`useGetMessagesByConvoId`, `/tmp/LibreChat/client/src/data-provider/Messages/queries.ts:8-42`) is configured with:

```typescript
refetchOnWindowFocus: false,
refetchOnReconnect: false,
refetchOnMount: false,   // ← the killer
```

`refetchOnMount: false` means: once messages are in the React Query cache for a given `conversationId`, they are NEVER re-fetched on mount — even if the data is stale. The only way the cache updates are:

1. **Initial fetch** — first time `ChatView` mounts for a conversation with no cache entry (e.g., new browser session, or conversation not visited yet in this session).
2. **SSE `done` event** — `useEventHandlers.ts:490-492` calls `setFinalMessages(conversationId, [...currentMessages, requestMessage, responseMessage])` which calls `queryClient.setQueryData`. This OVERWRITES the entire cache for that conversation with the NEW pair of messages (user request + AI response). Any message that was never in the cache is permanently excluded.
3. **`queryClient.invalidateQueries`** — only triggered by: user search, new chat, agent detail panel close, or a 404 on stream resume. None of these are triggerable from our backend.

**Why the 15-00 probe worked:** Sebastian navigated to "Drawing Assistance Alternatives Offered" FRESH in a new session. The cache was empty → initial fetch fired → picked up the synthetic message. This is NOT the production scenario.

**Why production fails:** Manuel was actively chatting. The messages cache was populated. After `sendBonusOfferMessage` inserted to MongoDB, the cache was never invalidated. When Manuel sent his next message, the SSE done event called `setFinalMessages([...cache, userMsg, aiResponse])` — where `cache` did not include our synthetic. The synthetic was silently dropped from the React Query state.

### Secondary: `messageId` uses hex ObjectId string instead of UUID v4

Real LibreChat messages use UUID v4 format (`5b92bec0-53a0-48e4-b58b-60328991a43e`). Our code uses `new ObjectId().toString()` which produces a 24-character hex string (`69da02eaf10ab23bfa285374`).

This is NOT the render blocker (the MongoDB API route does not filter by messageId format, and `buildTree` has no UUID validation). However it IS a correctness issue — the unique index `{ messageId: 1, user: 1, tenantId: 1 }` expects string values and can silently conflict if we re-insert with the same ObjectId-derived hex.

## Fix Options

### Option 1 (Recommended): Use UUID v4 messageId + Fix the Cache via `POST /api/messages/:conversationId` with JWT Impersonation

**What it changes:**
- `sendBonusOfferMessage`: change `messageId: new ObjectId().toString()` → `messageId: uuidv4()`
- After DB insert, call LibreChat's `POST /api/messages/:conversationId` with a JWT token generated for the kid user
- BUT: this endpoint does NOT trigger browser cache refresh either

**Why this alone does NOT solve the problem:** Even calling LibreChat's official POST endpoint does not push data to an active browser session's React Query cache.

**Verdict: INCOMPLETE — does not solve the realtime rendering problem.**

---

### Option 2: Fix the messageId format + Accept Delayed Display (Session-Restart visibility)

**What it changes:**
- `sendBonusOfferMessage`: change `messageId: new ObjectId().toString()` → `messageId: uuidv4()`
- No other changes

**Why it works (partially):** Our message IS in the DB with a valid UUID messageId. On the kid's next FRESH session (new browser tab, page refresh, or >5 minute navigation away and back), the React Query GC clears the cache → fresh fetch → message appears.

**Why it doesn't fully work:** During an active session where the kid was already chatting, the cache is stale. The message won't appear until cache expiry or manual refresh.

**Verdict: PARTIAL — message visible on next session, not immediately.**

---

### Option 3 (Recommended): Agent-Delivered Messages via System Prompt Flag

**What it changes:**
- Remove `sendBonusOfferMessage` direct-insert approach entirely
- When budget threshold hit, write a flag to MongoDB: `balance_state.pendingAgentMessage = { text: "...", insertedAt: Date }`
- Add a tool to the agents' toolset that our admin registers: `check_kidschat_status` — returns any pending message for this user
- The agent, instructed in its system prompt, calls this tool at the start of each turn and delivers any pending message
- After delivery, clear the flag

**Why it works:** Uses LibreChat's native SSE pipeline. Message delivered through the real AI streaming mechanism. React Query cache updated by SSE done event. Kid sees message in real-time.

**Risks/failure modes:**
- Requires adding a tool to all 4 agents (agent config changes in MongoDB)
- Agent might wrap the message in extra text ("Of course! I have an important message for you...")
- Tool call latency adds ~1s before message delivery
- Complex to implement

**Verdict: WORKS but requires agent modifications and has UX unpredictability.**

---

### Option 4 (Recommended): Lightweight `window.postMessage` Polling via Custom Endpoint

**What it changes:**
- Add a `GET /api/budget-notification?userId=...` endpoint to our Next.js admin service that returns pending notifications as SSE
- Add a tiny `<script>` snippet to LibreChat's HTML via a reverse proxy (nginx) that subscribes to this endpoint and calls `window.postMessage` → `queryClient.invalidateQueries`

**Why it works:** Forces React Query cache invalidation on the exact conversation.

**Risks:** Requires modifying LibreChat's HTML delivery (nginx config or custom middleware). NOT vanilla LibreChat. Rejected by constraint.

**Verdict: WORKS but violates vanilla LibreChat constraint.**

---

### Option 5 (Recommended): Fix messageId to UUID + Trigger UI Refresh via Reloading conversationId Parameter

After direct DB insert, UPDATE the conversation's `updatedAt` AND set a custom field on the conversation document that the LibreChat frontend would poll. There is no such polling mechanism in LibreChat's conversation query (all `refetchOnMount: false`).

**Verdict: DOES NOT WORK — no polling mechanism in LibreChat frontend.**

---

### Option 6 (Best Practical Fix): Fix messageId to UUID v4 + Call LibreChat's `/api/messages/:conversationId` via Generated JWT

**What it changes:**
1. Fix `messageId` to use `uuidv4()`
2. In `sendBonusOfferMessage`, after DB insert, also call LibreChat's `POST /api/messages/:conversationId` with a JWT generated for the kid user

Wait — this still doesn't refresh the browser. The POST endpoint saves to DB (already done by our insertOne) and does NOT emit SSE.

**Verdict: Same as Option 2 — PARTIAL.**

---

### Option 7 (Best Practical Fix, Revised): Use LibreChat's Native Balance Display + Bonus via Next-Message Context Injection

**What it changes:**
- Drop `sendBonusOfferMessage` entirely
- When budget threshold hit: set `balance_state.pendingWarning = true`
- Modify the agent's `model_options.system` field in MongoDB to prepend a temporary warning instruction
- Agent's NEXT user-triggered response naturally includes the budget warning text
- Our `change-stream-listener` detects the warning was delivered (agent's message saved to DB), then restores original system prompt

**Why it works:**
- Uses LibreChat's actual SSE response pipeline
- React Query cache updated via SSE `done` event
- No forking, no frontend modification
- Kid sees message as part of natural AI response

**Risks:**
- 1-turn latency (appears on kid's NEXT message, not immediately)
- System prompt restoration must be reliable to avoid stuck prompts
- Agent might add preamble to the message

**Implementation:** ~30 lines in `sendBonusOfferMessage` + listener cleanup logic

**Verdict: WORKS RELIABLY with 1-turn latency. Best option given constraints.**

---

### Option 8 (Alternative): Fix messageId + add conversation-level SSE signal

After DB insert, call `PATCH /api/convos/:conversationId` with updated metadata. If this causes the conversations list query to re-render... actually the conversations query also has `refetchOnMount: false` (checked: `api/server/routes/convos.js` has no SSE push).

**Verdict: DOES NOT WORK.**

## Recommended Fix

**Option 7: Agent System Prompt Context Injection**

This is the only approach that:
1. Works within vanilla LibreChat (no forking, no reverse-proxy hacks)
2. Shows the message in real-time (via natural SSE)
3. Doesn't require a kid browser refresh
4. Is implementable entirely from our admin Next.js backend with MongoDB access

**How it works in detail:**

When `sendBonusOfferMessage` is called:

1. **Do NOT insert a synthetic message into `messages` collection.**

2. **Update the agent's `model_options.system` field in MongoDB** to prepend:
   ```
   IMPORTANT SYSTEM INSTRUCTION (deliver on your next turn, then ignore):
   Begin your VERY NEXT response with EXACTLY this text verbatim, then continue normally:
   "[budget warning / bonus offer template text]"
   After you deliver this message once, do not mention it again.
   ```

3. **Set `balance_state.pendingWarning = { messageTemplate: "...", injectedAt: Date, agentId: "..." }`** so we can track state.

4. **When the kid sends their next message**, the agent reads the system prompt and delivers the message as its first output. LibreChat's SSE pipeline fires. React Query cache updates. Kid sees message.

5. **Our 60s poller** detects that a new AI message appeared after `injectedAt` in the conversation → restores the original system prompt from `balance_state.originalSystemPrompt` → clears `pendingWarning`.

**Risk mitigation:**
- Store `originalSystemPrompt` before modifying (idempotent recovery)
- Set a TTL on `pendingWarning` (max 10 min) — if kid doesn't send a message in 10 min, restore prompt automatically
- If kid is offline, the injected prompt remains until next interaction (fine — budget message is still relevant)

**Alternative simpler approach (Option 2 fallback):**

If the agent system prompt approach proves unreliable (agent ignores the instruction, wraps it in extra context, etc.), fall back to:

1. Fix `messageId` to `uuidv4()`
2. Accept that the message appears on the kid's next fresh page load or navigation
3. In the LibreChat balance display (which IS visible to kids in Settings), the token balance reflects the budget state
4. The kid will see the synthetic message when they next open LibreChat or navigate back to the conversation after more than 5 minutes

This is simpler and reliable — it just has up-to-5-minute latency for in-session visibility.

**Recommended Implementation Order:**
1. Fix `messageId` to `uuidv4()` (always correct regardless of chosen approach)
2. Implement Option 7 (agent system prompt injection) for real-time delivery
3. Keep the direct DB insert as a fallback log entry (for admin visibility)
