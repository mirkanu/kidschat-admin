# Phase 15.1 — Cost Cap Rewrite + Native Balance Integration

## Why this phase exists

Phase 15 shipped a working enforcement pipeline built on polling crons, a custom `cost_ledger` collection, and ACL-based locks. During user verification of Plan 15-02, three things surfaced:

1. **Scope shift** — user wants `dailyImageLimit` + `dailyMessageLimit` replaced with a single `dailyCostCapEur` (and monthly cap)
2. **New UX** — kids must see their own usage progress; 70% warnings delivered in-chat
3. **Architectural realization** — LibreChat's native `balances.tokenCredits` system (enabled in 15-01) already does "check on every kid interaction, block when out of credit". The 5-cron polling design in Phase 15 is doing work LibreChat already does natively.

## Architecture decision

**Lean on LibreChat's native balance system as the single source of truth for cost enforcement.** Phase 15's `cost_ledger`, `cost-ledger-sweep`, `limit-enforcement`, `enforcement.ts` lock logic, and `bonus-detection` cron are all removed or drastically simplified. What's left:

### Data model
- **`balances.tokenCredits`** (already exists, LibreChat-managed) — current remaining credit, auto-deducted per request by LibreChat
- **`settings`** collection — new shape:
  ```
  { key: "global_defaults", dailyCostCapEur, monthlyCostCapEur, bonusPackEur, weeklyBonusCapEur }
  { key: "child_override", userId, dailyCostCapEur?, monthlyCostCapEur?, ...}
  ```
- **`balance_state`** (new, small) — per-child bookkeeping that LibreChat doesn't track:
  `{ userId, lastDailyReset, lastMonthlyReset, monthlySpendEur, activeOfferMessageId?, activeOfferExpiresAt? }`
- **`bonus_purchases`** — kept roughly as-is
- `cost_ledger` — **removed**
- `locked_acl_entries` — **removed** (no more ACL-based locking for cost caps)

### Enforcement flow
1. At daily reset (00:00 UTC): `tokenCredits = eurToTokens(dailyCap + activeBonusCredit)`, record `lastDailyReset`
2. Kid sends messages. LibreChat deducts `tokenCredits` per request automatically.
3. When `tokenCredits` hits 0, LibreChat blocks the kid natively. **No cron intervention needed.**
4. Monthly reset (1st UTC): top up month-level accounting; re-apply daily cap for day 1

### Bonus offer + "YES" detection + 70% warning
**Recommendation: Next.js 15 `instrumentation.ts` + Mongo change stream listener, running in the same process as the admin Next.js server.**

- `src/instrumentation.ts` exports `register()` — runs once on server startup
- On register, open a change stream on the `messages` collection filtered to child user inserts
- On each new kid message event:
  - Recalculate remaining credit as a fraction of daily cap
  - If crossed 70% threshold (and not already warned today): insert synthetic warning message via Pattern 8
  - If kid replied "YES" within 5 min of an active offer (tracked in `balance_state.activeOfferMessageId`): credit `bonus_purchases`, top up `tokenCredits`, clear offer
  - If kid's `tokenCredits` just dropped to 0 for the day (and monthly cap not yet hit): insert bonus offer, record in `balance_state.activeOfferMessageId`

**Why this is the zero-touch option:**
- No additional Railway services to create (runs inside the already-deployed admin service)
- No additional cron scaffolding
- Instant reaction (~1s) instead of up-to-2-minute polling delay
- User sees progress reflect native LibreChat UI without any new frontend work

**Risks to verify in research phase:**
- Does Railway's managed MongoDB support change streams? (Requires replica set config — most managed MongoDB does, need to confirm for Railway specifically)
- Single-replica constraint: if admin service scales horizontally, multiple listeners would double-process. Acceptable now (1 replica default); add a warning in deploy docs.
- Process crash recovery: store `resumeToken` to disk/env on each event so restart replays from last seen event.

**Fallback if change streams don't work on Railway mongo:** 1 cron service running `* * * * *` that calls `/api/cron/tick` — still simpler than current 5-cron design. Requires 1 Railway service creation.

### Crons remaining
- **`/api/cron/daily-reset`** — 1 service, `0 0 * * *`, tops up tokenCredits to daily cap for every child
- **`/api/cron/monthly-reset`** — 1 service, `0 0 1 * *`, resets monthly spend accounting

These are both small and tolerate missed runs. Configured via `railway.toml` per the config-as-code reference.

## Kid-facing UX (native, free)

LibreChat's balance feature **already renders `tokenCredits` in the sidebar** when `balance.enabled: true`. No frontend work required — kids see their remaining credit as a token count. Open question: do we want to show this as "€ remaining" or keep it as "tokens"? If €, need to patch LibreChat's frontend or accept the token display.

**Recommendation:** ship with LibreChat's native token display in 15.1; evaluate if user wants € display as a follow-up once the architecture is validated.

## Admin-facing UX

- Dashboard top-level card: "Today's spend per child" — reads `balances.tokenCredits` + daily cap, shows progress bars for Sebastian + Penelope at a glance
- `/settings` — simplified: one global `dailyCostCapEur` + `monthlyCostCapEur`, per-child override table (this time it'll work because the schema is simple)
- `/users/{userId}` — already exists from 15-02; swap out the 5 usage bars for 2 (daily spend, monthly spend) driven by `balances` + `balance_state`
- Nav link to user detail: **already fixed in 15-02** (commit 927b5ee)
