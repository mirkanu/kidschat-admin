<objective>
Protect parent oversight by ensuring deleted conversations are recoverable, and fix preset icon visibility on LibreChat's dark sidebar.

Purpose: A 14-year-old can currently hard-delete conversations from MongoDB via LibreChat's sidebar, erasing them from the admin dashboard. This defeats the core safety value of the product. Additionally, the Phase 16 lucide icons are black-on-transparent and nearly invisible on the dark sidebar.

Output: (1) Research notes on LibreChat's delete mechanism, (2) a conversation archival system that preserves deleted conversations for admin viewing, (3) optionally a CSS-based delete button hide as a first layer, (4) white/light icon URLs in the Gist config, (5) Railway redeployment of both services.
</objective>

**Step 1 — Find LibreChat's delete API endpoint:**
Fetch LibreChat v0.8.4 source to find the delete route. Check these files:
- `api/server/routes/convos.js` or similar (conversation routes)
- Search for `delete` + `conversation` in the API routes
- Determine: What HTTP method + path? (likely `DELETE /api/convos/:id` or `DELETE /api/convos/clear`)
- Determine: Does it hard-delete (remove documents) or soft-delete (set a flag)?
- Determine: Does it delete from `conversations` collection only, or also `messages`?

Use: `curl -s "https://raw.githubusercontent.com/danny-avila/LibreChat/v0.8.4/api/server/routes/convos.js"` and related files. If that specific tag doesn't exist, try `main` branch.

**Step 2 — Check if LibreChat has added a delete toggle since v0.8.4:**
Check the latest LibreChat `main` branch config schema for any new delete-related toggles:
```bash
curl -s "https://raw.githubusercontent.com/danny-avila/LibreChat/main/packages/data-provider/src/config.ts" | grep -i -C5 "delete"
```
If a toggle now exists, note it — we may be able to upgrade or backport the config key.

**Step 3 — Check if `customCSS` or `style` exists in the interface schema:**
Search the config schema for any CSS injection capability:
```bash
curl -s "https://raw.githubusercontent.com/danny-avila/LibreChat/main/packages/data-provider/src/config.ts" | grep -i -C3 "css\|style\|custom"
```
If `customCSS` exists, it can hide the delete button as a quick first layer (non-security, just UX friction).

**Step 4 — Verify Railway MongoDB limitations:**
Confirm change streams are still unsupported:
```bash
railway run --service kidschat-admin mongosh --eval "db.getMongo().watch()" 2>&1 | head -5
```
(This is expected to fail with error 40573. If it succeeds, change streams are now available and we should use Approach A instead.)

Alternative: just confirm from STATE.md that the decision from Phase 15 still holds (Railway MongoDB standalone, error 40573, no change streams). If the admin app can connect to MongoDB, try a quick test. If not accessible externally, trust the Phase 15 finding.

**Step 5 — Evaluate approaches and choose:**

Given Railway MongoDB constraints (no change streams, no Atlas triggers), evaluate:

| Approach | Feasibility | Reliability | Complexity |
|----------|-------------|-------------|------------|
| A. Change stream archive | BLOCKED if Railway MongoDB still standalone | High | Medium |
| B. Atlas/Percona trigger | BLOCKED (Railway uses community MongoDB) | High | Low |
| C. API proxy intercept | Feasible but fragile (routing complexity) | High | High |
| D. Periodic snapshot cron | Always feasible | Medium (data loss window) | Low |
| E. Oplog reading | Likely blocked (same as change streams) | Medium | High |
| F. CSS hide delete button | Feasible if customCSS exists | Low (devtools bypass) | Minimal |

**Recommended approach: D (periodic snapshot) + F (CSS hide if available)**

D provides server-side backup: a Railway cron runs every 5-10 minutes, snapshots all conversation IDs + metadata to a `conversation_snapshots` collection. If a conversation disappears from `conversations`, the admin dashboard detects it was deleted and can still show the archived copy. The data loss window is at most one cron interval (a conversation created and deleted within 5 minutes could be lost — acceptable for a family app).

F adds UX friction: if LibreChat supports `customCSS`, inject `display: none` on the delete button. This stops casual deletion even if it's bypassable by a tech-savvy teen.

**Alternative approach worth checking:** Instead of periodic full snapshots, use a differential approach — on each cron tick, query `conversations` for all docs, compare against a `conversation_index` collection that tracks known conversation IDs. Any ID in the index but missing from `conversations` was deleted. Then the cron can query `messages` for those IDs before they're garbage-collected (if LibreChat deletes conversations first, messages might linger briefly — or might be deleted atomically).

**CRITICAL insight to verify:** Does LibreChat delete messages when it deletes a conversation? If messages are left orphaned, the cron just needs to track conversation metadata — the messages are still in MongoDB. If both are deleted atomically, the cron must snapshot both.

2. Whether messages are deleted with conversations or separately
3. Whether any new config toggle exists

5. Chosen approach with rationale
6. Implementation plan for Task 2
